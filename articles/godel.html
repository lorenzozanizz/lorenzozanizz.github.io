Gödel and Lean: can we discuss formal language inside a formal language?

Lean is both a programming language and a theorem prover. That makes it a natural place to ask a slightly strange question: can we use one formal language to define another formal language, talk about proofs in that language, and then construct a sentence which, in some sense, talks about its own provability?

This is the territory of Gödel's incompleteness theorems. A full formalization is a serious project: one needs an arithmetic theory, a coding of formulas and proofs by natural numbers, a formal proof predicate, substitution, representability results, and the diagonal lemma. Instead of reproducing all of that here, I want to build a deliberately small Lean model which captures the shape of diagonalization while being very explicit about what it leaves out.

The result is not a full proof of Gödel's theorem. It is a model of one of its central mechanisms: constructing a formula G whose interpretation satisfies G ↔ ¬Provable(G).

First: what Gödel's theorem is actually about

Gödel's first incompleteness theorem concerns sufficiently expressive, effectively axiomatized formal theories. Very roughly, once a consistent theory can express enough arithmetic, there are statements in its language that it cannot settle. Modern presentations often use the diagonal lemma: for a formula A(x) with one free variable, one can construct a sentence D such that the theory proves D ↔ A(⌜D⌝), where ⌜D⌝ denotes a code for the syntax of D.

The Stanford Encyclopedia of Philosophy gives exactly this formulation of the diagonalization lemma and emphasizes an important point: this is a provable equivalence, not a magical sentence literally containing itself as text. Its supplement on diagonalization explains the key operation in terms of substitution on Gödel codes.

For incompleteness, we eventually choose a property such as A(x) := ¬Prov(x). The resulting fixed point behaves like: 

G ↔ ¬Prov(⌜G⌝)

Informally, people say that G "says that it is not provable". That phrase is useful, but it should not be confused with the liar sentence L ↔ ¬L. Gödel's construction concerns provability in a specified formal system, not direct negation of the sentence itself.

Lean lets us build a language as data

Lean is well suited to this experiment because we can represent the syntax of another language using inductive datatypes. This is standard Lean: its documentation introduces inductive types as the basic mechanism for constructing recursive datatypes, and its propositions-and-proofs chapter explains how logical propositions themselves live inside Lean's dependent type theory.

The first distinction to keep clear is therefore: 

Lean                    -- the host language / metatheory
└── MiniGodel.Formula   -- syntax of a tiny object language represented as Lean data

Our toy language will be intentionally tiny. It contains only falsehood, implication, and a predicate intended to mean "the formula represented by this term is provable". Negation does not need to be primitive: ¬P can be represented as P → ⊥. 

namespace MiniGodel

mutual
  inductive Term : Type where
    | var   : Term
    | quote : Formula → Term
    | diag  : Term → Term

  inductive Formula : Type where
    | bot  : Formula
    | imp  : Formula → Formula → Formula
    | prov : Term → Formula
end

open Term Formula

def negF (p : Formula) : Formula :=
  .imp p .bot

This already contains the biggest shortcut in the article: quote and diag are primitive constructors in our toy syntax. In an actual Gödel proof, they are not free operations. Formulas and proofs are encoded by natural numbers, and one has to show that the relevant operations on those codes are arithmetically representable.

What does "diagonalization" mean?

Suppose we have a formula with one free variable: 

A(x)

Think of x as a slot into which we can place the code of a formula. If we can mechanically substitute a formula's own code into such a slot, we can create a fixed point.

The characteristic construction is: 

start with A(x)
build a template δ(x)
then form δ(⌜δ⌝)

The clever part is arranging δ so that the code produced inside it refers to the final sentence. The diagonal lemma guarantees that this can be done in sufficiently strong arithmetical theories.

In our toy Lean model, I do not prove that arithmetic can perform this coding. I implement the operation directly. First, substitution replaces the free syntax variable by another term: 

mutual
  def substTerm (replacement : Term) : Term → Term
    | .var       => replacement
    | .quote f   => .quote f
    | .diag t    => .diag (substTerm replacement t)

  def substFormula (replacement : Term) : Formula → Formula
    | .bot       => .bot
    | .imp p q   =>
        .imp
          (substFormula replacement p)
          (substFormula replacement q)
    | .prov t    =>
        .prov (substTerm replacement t)
end

Notice that substitution does not enter quote f. Quoted syntax is treated as data. This is analogous to the difference between a variable in a program and the same characters appearing inside a string literal.

Now we give terms an interpretation. The interesting case is diag: 

def evalTerm (ρ : Formula) : Term → Formula
  | .var =>
      ρ

  | .quote f =>
      f

  | .diag t =>
      let f := evalTerm ρ t
      substFormula (.quote f) f

This definition is the toy version of diagonalization. Given a term denoting a formula f, it replaces the free variable of f by the quotation of f itself.

In informal notation: 

diag(⌜f⌝)  ↦  f(⌜f⌝)

That is the self-application step. Again, in a real incompleteness proof this operation is encoded as arithmetic on natural numbers. Here Lean simply computes it on syntax trees.

Building the Gödel-shaped sentence

Next we give our formulas a semantics. The meaning of Prov(t) is supplied by an external Lean predicate Provable : Formula → Prop: 

def Holds
    (Provable : Formula → Prop)
    (ρ : Formula) :
    Formula → Prop
  | .bot =>
      False

  | .imp p q =>
      Holds Provable ρ p →
      Holds Provable ρ q

  | .prov t =>
      Provable (evalTerm ρ t)

This is another major simplification. In a genuine Gödel formalization, provability is itself arithmetized: one defines a relation such as Proof_T(p, n), meaning that p codes a valid proof in the theory T of the sentence coded by n, and then: 

Prov_T(n) := ∃ p, Proof_T(p, n)

Our toy model skips that entire layer and lets Lean provide Provable from outside.

Now define the idea "this represented formula is not provable": 

def psi : Formula :=
  negF (.prov .var)

Conceptually: 

ψ(x) = ¬Prov(x)

We then make the diagonal template: 

def delta : Formula :=
  negF (.prov (.diag .var))

so: 

δ(x) = ¬Prov(diag(x))

Finally, substitute the quotation of delta into delta itself: 

def G : Formula :=
  substFormula (.quote delta) delta

Lean can reduce the resulting syntax: 

theorem G_shape :
    G =
      .imp
        (.prov (.diag (.quote delta)))
        .bot := by
  rfl

The crucial computation is that diag(quote delta) denotes G: 

theorem diagonal_points_to_G (ρ : Formula) :
    evalTerm ρ (.diag (.quote delta)) = G := by
  rfl

Therefore, under our semantics, G has exactly the fixed-point property we wanted: 

theorem godel_spec
    (Provable : Formula → Prop) :
    Holds Provable .bot G ↔
      ¬ Provable G := by
  rfl

The fact that this proof is just rfl is not evidence that Gödel's theorem is trivial. It means that we deliberately designed the toy syntax and its diag operator so that the fixed-point equation is true by computation. The difficult theorem that Gödel proves is that ordinary arithmetic can encode enough syntax and computation to obtain the same effect without a built-in diag instruction.

Why this is not a contradiction

Our sentence has the form: 

G ↔ ¬Provable(G)

It does not have the form: 

G ↔ ¬G

The distinction between truth and provability is the whole point. A statement can fail to have a proof in a particular theory without being false.

If we additionally define a proof relation and assume that the proof system is sound for our semantics, then a proof of G would imply that G is true. But the truth condition for G says that G is not provable. So, under that soundness assumption, G cannot be proved. 

assume Provable(G)
        ↓
soundness
        ↓
G
        ↓
meaning of G
        ↓
¬Provable(G)

This is enough to illustrate the tension, but it is not the standard first incompleteness theorem in its full technical form. My small argument assumes semantic soundness, which is stronger and simpler than the hypotheses normally used in Gödel or Rosser incompleteness results.

What has been implemented, and what has not

The experiment really does implement syntax trees, substitution, quotation, a diagonal/self-substitution operation, a semantics for the tiny language, and a fixed point whose interpretation is G ↔ ¬Provable(G).

But the following parts are intentionally missing:

  • Gödel numbering of formulas as natural numbers;
  • an actual arithmetic theory such as Peano Arithmetic;
  • coding of finite proofs as natural numbers;
  • an arithmetized predicate Proof_T(p, n);
  • a proof that substitution and proof checking are representable in arithmetic;
  • a derivation of the diagonal lemma from those arithmetic encodings;
  • the full hypotheses and conclusion of Gödel's or Rosser's incompleteness theorem.

In other words, the toy system makes the central syntactic operation primitive: 

toy model                     full Gödel construction

Formula datatype          →   natural-number Gödel codes
quote φ                   →   numeral for ⌜φ⌝
diag                      →   encoded substitution function
Provable : Formula → Prop →   ∃ p, Proof_T(p, n)

The full theorem is remarkable precisely because the right-hand column can be constructed using arithmetic itself.

So, can a formal language discuss a formal language?

Yes, but there are several levels that should not be collapsed into one. 

Lean
│
│  defines and reasons about
▼
syntax of our object language
│
│  contains expressions such as
▼
Prov(t)
│
│  which we interpret using
▼
a proof relation / provability predicate

Lean is not confused by this. From Lean's perspective, our formulas are ordinary inductive data. Functions such as substitution are ordinary recursive programs. Statements about those functions are ordinary propositions checked by Lean's kernel.

This host-language/object-language separation is one of the useful ways to understand formal logic. We can use a formal system as a metatheory in which we define another system, its syntax, its proof rules, and properties of those proof rules.

One can go substantially further. The lean4-logic project develops propositional and first-order logic, arithmetic, computability machinery, and formal incompleteness results in Lean. Its summary includes a formal first incompleteness theorem and an explicitly constructed undecidable sentence. That is much closer to the full right-hand column above than this article's miniature model.

There is an additional recursive-looking twist: implementations such as Lean4Lean implement a Lean 4 kernel checker largely in Lean 4 itself. That is a different problem from Gödel incompleteness, but it reinforces the same conceptual lesson: formal languages can represent and manipulate descriptions of formal languages, including languages closely related to themselves.

The theoretical lesson

The profound step in Gödel's argument is not the use of exotic logical connectives. In fact, our toy language needed very little propositional logic. The hard part is turning syntax into data and making operations on syntax available inside arithmetic.

Once formulas, substitutions, and proofs can be encoded by numbers, arithmetic can express statements about arithmetic proofs. Diagonalization then produces fixed points: sentences related, by a theorem of the formal system, to claims about their own codes.

That mechanism does not make the formal system explode in contradiction. Instead, under the relevant hypotheses, it exposes a gap between two notions that are easy to conflate: 

truth in the intended interpretation
            ≠
provability inside a particular formal theory

Our Lean model only sketches that boundary. But even the sketch is useful because every layer is explicit: syntax is a datatype, quotation is a constructor, substitution is a function, diagonalization is an operation, and the fixed-point property is a theorem that Lean checks.

The part we cheated on is also completely visible. We handed the toy language quotation and diagonalization directly. Gödel's theorem earns its depth by showing how to reconstruct those capabilities through arithmetic coding instead.
